# 高质量自动化评估与通用适配路线

2026-09-27。此文是源码与已有验收记录的评估，不是启动整套开发或部署旧原型。当前发布线为 208；独立原型仍位于 `U:/code/DND-card-automation-dev`，基于旧 193，需要挑选纯规则部分迁移，不能整树合并。

## 现状：具备部分规则核心，缺完整执行系统

原型已有：纯修饰器运算、基础值和派生值分离、来源追踪、装备/同调条件、AC 候选、属性上下限、部分攻击/豁免骰子修正、显式临时效果与游戏时间，以及 JSON 保存。原型的 195 项单元和 13 项浏览器记录是历史证据，不是当前线上验收。

封存记录还保留了空分组取首项导致整卡崩溃、身份格缺项提示、部分子职/施法属性选择、触摸交互等未完成项。因此应迁移可复用的纯规则代码，再按现行手动填写模式接界面；不能把旧实验界面直接恢复到正式站，也不能用历史绿灯跳过这些已知问题。

当时转换器报告扫描 4,055 条记录，其中 2,369 条在持续数值范围内；7,322 个判断点有 2,399 个被支持（32.8%）。这是固定快照的字段/转换判断点统计，既不是 32.8% 的 Wiki 条目完整可用，也不是总工程完成 32.8%。例如“不支持”中有 857 项是来源元数据，415 项属于附带法术授予，285 项属于恢复方式，282 项属于充能；不能把这些全部当作数值引擎缺陷，分母需要按功能重新整理。

以下缺口决定目前还不能称为完整自动化：

| 能力 | 当前状态 | 需要补齐 |
| --- | --- | --- |

| 武器攻击 | 线上能记录并保留公式，转换丢失已修 | 属性选择、熟练、魔法加值、近战/远程/投掷、多用、装备自动生成快捷攻击 |

| 数据适配与创作 | 固定转换器和自定义 JSON 入口 | 分版本规则包、校验器、可视化规则编辑、未支持报告、规则包迁移与差异审阅 |

## 面向上万条内容的适配方法

实现可组合的规则机制，一类机制覆盖许多条目。规模重点是不同机制及其组合，不是单纯条目数量；大量描述性 Wiki 内容本来也不需要执行。

建议管线：原始资料 → 来源/版本/稳定身份归一化 → 规则族转换器 → 统一规则定义 → 校验及覆盖报告 → 纯求值/动作计划 → 权威提交 → 卡片与棋子展示。

统一定义至少分成五类：

1. **持续修正**：目标、加法/乘法/覆盖/上下限、条件、优先级、堆叠组、来源。
2. **授予与选择**：来源、等级门槛、候选范围、选择数量、授予对象及撤回规则。
3. **可执行动作**：触发、目标、攻击/豁免、公式、消耗、结果、可选替代支付方式。
4. **资源**：上限、剩余、恢复条件、消耗事务；绝不能由重新计算恢复次数。
5. **效果实例**：施加者、目标、开始时刻、持续时间、结束条件、专注/叠加关系。

护甲可用“装备条件 + AC 方案 + 敏捷上限”表达；盾牌用“持用条件 + 版本训练门槛 + AC 加值 + 同组限制”；力量下限物品用“同调条件 + 属性 minimum”；来源法术用“等级门槛 + 授予 + 始终预备/次数 + 施法属性”。同类新条目只增加参数和规则数据，不能在 UI/核心里增加 `if (中文名 === 某物品)`。

优先级由资料质量决定：

- 已有结构化字段：直接按通用规则族转换。
- 上游 effects/activities/advancement：转换其语义，保留版本和来源；平台专有行为不能仅改字段名就视为支持。
- 可识别模板：用版本化模板转换，提供代表例和反例。
- 只有自然语言：AI 可离线辅助生成受限规则定义、引用依据和候选测试，由校验/审阅后入库；运行时只执行确定的规则，不让模型临场读正文后直接改角色或掷骰。
- 全新特殊机制：添加可复用机制或保留人工处理。少量真正特殊的行为允许隔离扩展，但必须按稳定规则身份绑定、有测试、有来源，不能散落在页面里。

“尽量少逐条编码”可以做到；“任意第三方自然语言从此永远无需新语义”没有可靠保证。新机制首次出现时，仍需要定义它怎样与已有机制交互。

## 必须有的使用体验

- 每个数值都能查到基础值、来源、生效条件、未生效原因和人工修正。
- 操作前明确目标与消耗，成功只执行一次；中断时能看清已提交哪部分。
- 遇到未知规则显示人工处理，不给错误的“全自动”结果。
- 升级、卸装、失去来源、撤销、刷新、重新导入均不重复授予、不误删独立获得的同名条目。
- 自动化按角色/功能分级启用；旧卡先复制预览差异，不突然改写多年手填数据。
- 保留五页 A4 外观。固定法术使用有来源的特殊框，不强迫改成向导或通用仪表盘。

## 推荐排期与验收

先做全库只读盘点，把条目按“描述性/数值/授予/资源/动作/触发/外部依赖/待解释”分类。报告至少同时统计条目完整支持、机制支持、仅部分支持、无须自动化、未支持原因和来源版本；不以字段识别数冒充规则正确率。抽样手工核对，避免转换器用自己的结果证明自己。

| 阶段 | 交付 | 粗估工作量 |
| --- | --- | --- |
| 0 | 盘点、固定协议、迁移边界、保存一致性与故障用例 | 1–2 开发周 |
| 1 | 用户四项：护甲/盾牌、武器快捷攻击、来源固定法术，完成本机闭环 | 2–4 开发周 |
| 2 | 角色成长、常驻修饰、资源/休息、规则创作与覆盖报告 | 3–6 开发周 |
| 3 | 目标/施法/效果/专注/战斗结算与多人可靠性 | 6–12 开发周 |
| 4 | 第三方长尾、新机制、性能与长期兼容 | 持续迭代，盘点前不承诺封顶 |

这些是按一名持续投入的开发者、有用户配合实测、2014/2024 均保留的工程量区间，**不是日历承诺或已测出的耗时**。部分工作可重叠；常用高质量版本属于多周工作，广泛战斗自动化按数月规划更稳妥。第一轮机制盘点后才能把区间缩小。不能用“上万条 × 每条若干分钟”估价，也不能承诺导入一个现成库即全部完成。

每阶段都要有手算/权威示例、真实来源样本、组合与撤销用例、未知规则反例、持久化失败注入、真实浏览器流程。多人阶段必须再做真实房间的多客户端权限、丢包、迟到消息和重连测试。每次只交付一个能体验、能核对、能回退的闭环。

覆盖报告要绑定资料快照和规则包版本，并按官方/第三方及 2014/2024 分组；中英文别名只用于查找，稳定身份才用于规则绑定。新资料进入时先生成语义差异与待审队列，不能悄悄替换旧角色所依赖的规则。私有上游快照与玩家资料不进入公开仓库或源码下载包。

## 能做到什么

可以持续实现这套通用引擎、转换器、覆盖报告、编辑工具和测试，并把常见机制按优先级迁入产品。高质量需要逐批实测和对歧义规则的明确裁定；我不能凭生成代码保证任意自然语言规则百分之百自动正确，也不能把模型自身生成的期望当成独立验收。
