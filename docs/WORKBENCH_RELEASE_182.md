## 已复现的原因

1. 总览资源的排队差异对比使用旧的已确认值。5→4 未确认时再点回 5，第二次被推断为空差异；实际第二条请求仍提交 4，没有有效资源变化和播报，刷新后回弹。真实 DMConsole/ResourceRow 点击在旧代码中稳定失败，记录在 resource-burst182/before-fix。
2. 人物文档已经提交，资源通知已经显示，但 command 继续等待棋子 updateItems 响应，阻塞 ACK 和后续写入。真实 SDK 双 iframe 夹具扣住响应可复现：只有第一笔保存，第二笔被挡住。
3. 通知已本地显示/广播后，等待广播调用的响应也会同样阻塞整个修改队列。独立扣留 NOTICE_CHANNEL 响应复现该窗口。

## 修改

- current/locked 按钮发送明确的字段意图；执行时合并最新资源的其余字段，保留资源预期值检查和撤销守卫。改回原值不再被错误折叠。
- 人物持久文档确认与棋子显示更新分开。后台按角色串行更新并合并到最新文档修订；旧投影与真实场景编辑仍由原 baseline/版本校验区分。resource/stats/save/condition 共用路径受保护，怪物仅存 metadata 的写入仍等待真正提交。
- 通知本地接收及远端发送保留唯一 ID 和隐私裁剪；广播应答不再占用已提交修改的确认队列。

资源和生命值控件还修复了结算期间收到更新权威值却不恢复显示、较旧数字回执造成短暂旧值写入的问题。只有提交后确实观察到权威数值变化并到达目标，才使用该确认解除等待；不会把 ABA 的旧原值误当新确认。
