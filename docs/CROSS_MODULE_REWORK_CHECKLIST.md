## 总体纪律

- [ ] 先从当前稳定基线创建独立分支，不直接在主线做大规模实验。
- [ ] 按下面的批次顺序推进；一批验收通过后再进入下一批。
- [ ] 每项都必须留下错误日志、关键状态和复现路径，禁止吞异常。
- [ ] 类型检查、构建成功不等于功能完成；必须在真实 Owlbear 房间验证。
- [ ] 至少完成 DM + 两名玩家的多客户端测试，并覆盖明暗主题。

- [ ] 不覆盖现有用户数据；涉及旧数据时必须明确迁移和回退方案。

### 1. 状态追踪性能与竞态

- [ ] 把 `OBR.scene.items.onChange` 当作完整场景快照处理，不重复读取全场。
- [ ] 合并短时间内的重复场景刷新，避免一次操作触发多次完整渲染。
- [ ] 同一个 Token 的状态写入必须串行，禁止并发互相覆盖。
- [ ] 替换相同稳定 ID 的气泡时，必须先确认旧气泡删除完成，再添加新气泡。
- [ ] 状态增删失败必须记录 Token ID、状态 ID、操作阶段和错误信息。
- [ ] 实测多人同时修改状态、快速增删同一状态、切换场景和重新加入房间。

### 2. 角色卡自动资源 ID

- [ ] 中文能力名生成的资源 ID 必须稳定且唯一，不能全部退化成 `auto-`。
- [ ] ID 应包含可读片段和稳定摘要；同一能力重复导入时保持一致。
- [ ] 绑定旧角色卡时检测空 ID、重复 ID，并提供可回退的兼容修复。
- [ ] 验证多个中文同名/近似名能力分别增减时不会串联。

### 3. 传送门首次移动

- [ ] 场景启动时为所有可拖动的 CHARACTER/MOUNT 建立坐标基线。
- [ ] 不依赖 selection watcher 异步预填旧坐标。
- [ ] 第一次拖动、启动时已选中、快速连续拖动都必须正确触发传送判断。
- [ ] 传送失败必须保留入口、目标、Token ID 和坐标日志。

### 4. 变身限制与兼容

- [ ] 测试角色卡 HP 与怪物 HP 两种计算模式及解除后的恢复结果。
