# Jolt 单线程 SIMD 可行性研究

研究日期：2026-10-10。结论：值得采用同版本的单线程 SIMD 构建，作为现有 Jolt 的计算升级。应保留原构建作为兼容回退，并先完成版本化资源和真实房间验收。本轮只构建、对照和验证候选，没有替换线上引擎。

实际基线是 Suite `1.0.272-dev`：运行源码 `5e55185e962cbbe070f4227f5a137843d01eacd9`，配套 Web `0b225940caa5e1b54c7afa3c9c000df149856c6d`，数据 `14a2282fe50cb92da3b5c667cb279b8f9efab3bc`。隔离研究从最新交接提交 `0d9cc2aec992066f810af9501fe432427b95f8cb` 开始；272 保留 271 的骰子源码。未重置原工作区，也未修改生产服务、Nginx、SSH、防火墙、网络或玩家数据。

**构建与复现。** 固定包装层 `JoltPhysics.js@1.1.0`（`c9c122bcd48e92885fbee7d267c928c3781d581c`）、核心 `JoltPhysics@5.6.0`（`e77f175595e64cb44218cc9d9d56fc365ad0e36a`）和 Emscripten `6.0.2`（SDK `ca38f487f28b7c3c16f8f70cd0e012099ac4b7e2`）。分别构建普通版与 SIMD 版，只改变 `ENABLE_SIMD`。两者均使用 `Distribution`、单线程、128 MiB 固定初始内存；LTO、双精度、内存增长和跨平台确定性开关均关闭。保留原浮点编译约束，没有启用 fast-math、relaxed SIMD，也没有改变步长、碰撞精度、落地判断、随机源或失败重算逻辑。[固定官方构建配置](https://github.com/jrouwe/JoltPhysics.js/blob/c9c122bcd48e92885fbee7d267c928c3781d581c/CMakeLists.txt)

重建普通版的 JS 和 WASM 与正式锁定文件逐字节一致，两个 SHA-256 都相同。因此可以排除同时升级编译器或构建参数的干扰。官方反汇编确认原版与重建普通版均无向量指令；SIMD 版含 123,642 条向量指令。三者内存声明均为 2,048 页、上限 2,048 页，无共享内存。

候选文件摘要为 JS `0c96580c54ac044a2d2d038f54a04e6a0b7d0e5a5aaef9a3aa9aa308965aa4d6`、WASM `deb7d04efa2b841a9e7b9a595214da6072cadc07802e52735e7fda69d130c245`。初始化继续校验配套的两份文件，不能据此把新 WASM 直接混入旧 glue。

**行为对照。** 在 Linux 和 Windows 分别执行三种构建的 47 个固定用例。覆盖全部骰型、d100 的两个实体、20 枚骰、19 枚混合骰的三次预测、24 个预先固定种子、横屏与窄竖屏、优势与劣势、真实保底和封顶翻面、强制重投、爆炸骰、既有权威结果及保留骰子碰撞。所有完整 Float32 轨迹逐位一致，点数、碰撞、重算次数及顺序和规则信息一致。两个系统之间的轨迹与元数据摘要也全部一致。排除的字段只有实际计时；没有缩短失败案例、改变随机种子或隐藏不利结果。

这证明已测样本的等价性，不能证明所有种子、CPU 架构或浏览器都等价。Windows 为 i5-9400F / Node 22.17.1；Linux 为 Xeon Platinum 8370C / Node 22.23.3。ARM、Firefox、Safari、旧 WebView 和实体手机尚未测试。

**计算耗时。** 下表来自[固定研究提交的成功 CI](https://github.com/FullPeople/obr-suite/actions/runs/38027912183)。编译结束后串行执行七轮预定交替顺序；每种构建、每个核心案例各七次。原版和重建普通版文件相同，汇总时合并其 14 次普通版观测，与七次 SIMD 观测比较，保留两组原始记录、范围和尾部数据。数值只衡量完整物理预测，包含相应失败重算，不包含网络、轨迹发送或实际首帧。

普通版的部分 20d6 观测有明显预热波动；原始观测范围和每轮记录保存在结果中，不以单次最快值代替总体。SIMD 的冷初始化加预热中位数为 249.8 ms；原版 267.3 ms、重建普通版 262.0 ms。本实验未发现冷初始化回退，但这是本地资源的 Node 测量，不代表公网完整冷启动。

**资源成本。** JS 大小保持 964,712 字节。WASM 从 2,021,569 字节增至 2,435,140 字节，增加 413,571 字节，约 404 KiB。按本地 gzip 默认最高等级对照，配套 JS 与 WASM 的合计大小从 876,003 字节降至 840,858 字节，减少约 34 KiB。公网正式 WASM 当前确实以 `application/wasm` 和 gzip 返回；压缩测试仍不是候选已上线的证据。运行时线性内存没有翻倍，也没有引入线程池或跨源隔离要求。

**浏览器验证。** 使用正式 SDK、真实 WASM、生产渲染代码和两个独立 Chromium 上下文。Windows Chrome 154 的实际 GPU 为 RTX 2070 / D3D11，没有请求软件渲染。SIMD 版通过七类混合骰、19 枚慢案例、丢失目标及真实未选中目标的投骰面板；两端结果一致，实际 GPU 像素随骰子运动变化，数字飞行动画通过。

普通版与 SIMD 版混合使用另做双向测试，分别让 Host 加载 SIMD、Player 加载普通版，以及 Host 加载普通版、Player 加载 SIMD。每端实际请求的 JS/WASM 摘要均与对应锁一致；测试单骰、9d6、私密结果和丢失最后一个数据包后的恢复。完整记录保存在浏览器证据目录。此处验证的是本地模拟房间中的两种物理构建，并非真实 Owlbear 房间、自然缓存升级或完整权威迁移验收。

Host SIMD / Player 普通版首轮通过。反向首轮完成四个投骰用例后，末尾检查发现一次 `peer-ping` 的 SDK 广播响应超过 5 秒；因此该轮整体失败，截图与完整诊断保留，没有忽略错误或放宽超时。反向使用相同代码和超时限制复测，四个用例及末尾错误检查通过，两个客户端实际加载摘要也通过。一次成功复测不能解释首次超时，原因尚未确认；继续列入真实房间与负载验收，不把它直接归因于环境或引擎。

本机同时有其他较重的计算任务，内存空闲量曾降至约 1 GB。普通版首帧与慢案例在重复测试中波动明显；浏览器数据可支持功能与回放兼容结论，不能用来宣布完整链路已经稳定加速。未测显示器最终呈现；GPU 同步读回本身也有开销。模拟网络为单向 10 ms，不能当作真实玩家网络。

**采用方案。** 在 Worker 中用最小 WASM 特征探针检测 SIMD，支持时只初始化 SIMD 构建，否则只初始化现有普通构建。保持现有资产摘要验证、权威协议、完整轨迹、规则翻面和保留碰撞体逻辑。两个版本均使用固定 SHA 和明确构建身份；候选资源使用独立版本路径，保留旧的 JS/WASM 地址，以便旧 Worker、已打开页面和旧缓存继续工作。更新资产校验、构建复制、缓存和发布验证，然后做自动回退、混合缓存、权威迁移、真实房间及移动端验收，再安排窄范围上线。

47 个样本的逐位一致和计算收益足以支持继续接入，不足以承诺“任何情况 0.3 秒”。在本实验的 19 枚三次预测案例中，SIMD 的计算本身仍约 0.41 秒；起播排队、发送、网络和绘制还需另计。
