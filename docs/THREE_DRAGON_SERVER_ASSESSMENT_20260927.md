# 2026-09-27 · 三龙牌操作延迟与自建服务器评估

结论：建议把牌局同步改为页面直连自有服务器，并将规则裁定、存档放到服务器；枭熊继续作为打开牌桌的入口即可。同步内容、历史记录和本地页面通道需要同时调整。现有服务器适合先做 10–20 桌的容量验证，不能把此数字当成已经压测通过的并发承诺。本轮仅评估，没有切换在线牌局或部署新服务。

用户确认的症状是出牌、准备、结算后长时间没有响应。不是本次针对鼠标帧率或首次资源下载的问题。网页和牌图本来已由 obr.dnd.center 提供，目前经过枭熊的是联机消息和本地页面/后台桥接。

## 现有链路里可以直接造成等待的机制

当前链路为：玩家牌桌页面 → 枭熊 LOCAL 广播 → 玩家插件后台 → 枭熊 REMOTE 广播 → 主持后台规则计算及 IndexedDB 保存 → 枭熊房间摘要读写 → 返回玩家后台 → 枭熊 LOCAL 广播 → 玩家牌桌页面。

- `broadcast.ts` 的同一发送队列强制每条消息相隔 150 ms。本客户端的 LOCAL 视图、REMOTE 私有快照和手势共用队列；限流重试会把间隔再加长。
- `wire.ts` 的 REMOTE 状态允许带入约 48,000 字节的近期历史包。`private-channel.ts` 再 AES-GCM 加密、Base64 编码、每 10,000 字符分包。枭熊官方文档说明广播数据上限 16 KB，LOCAL 与 REMOTE 是同一个广播 API 的不同目的地；150 ms 是本项目的保护策略，不是官方公布的速率数值。[官方 Broadcast 文档](https://docs.owlbear.rodeo/extensions/apis/broadcast/)
- `controller.ts` 成功后先向提交者回复一份带回执的完整快照，再向所有远端会话广播各自的完整快照；提交者会再次收到。每个合法动作还执行房间摘要读/写/再读以及初始检查。
- `local-view.ts` 已把普通本地视图历史限制到较小范围，REMOTE 仍是较大快照。此前减少 LOCAL 历史的修复没有消除此处瓶颈。
- `controller.ts` 默认 3 秒检查重试，12 秒心跳，24 秒离线判定。长队列与重试可能叠加；没有在真人房间捕获这次反馈的完整日志，不能断言每次重试都实际触发。

六人合成牌局使用现有引擎执行合法操作。在第 20 次操作时，单个座位快照已经约 47 KB，实际加密封包为 7 条。主持向另 5 人发送共 35 条，单以 150 ms 间隔计算，从第一条开始到最后一条至少约 5.1 秒。非主持提交者额外回复的 7 条让同次发送共约 42 条，对应约 6.15 秒发送队列跨度。它不等于每位玩家各自的最终延迟；提交者可能较早得到结果，而后续动作、其他玩家和本地页面更新仍受队列影响。此估算尚未加网络、元数据、手势、限流退避或额外观众。

## 自有服务器当前状态

2026-09-27 SSH 只读检查：2 个逻辑 CPU，Intel Xeon Platinum；系统可见内存约 1.58 GiB，可用约 612 MiB，无交换分区；磁盘剩余约 21 GB。检查时负载约 0.01 / 0.08 / 0.08，已有角色卡中继使用约 69 MiB。CPU 当时空闲，内存余量需要控制。这是当时快照，不能代表高峰。

公网带宽套餐和预期并发桌数未知，用户也暂不清楚。没有用网卡接口标称速率冒充购买的公网带宽，没有进行占满公网的测速。

## 真实服务器上的有界计算样本

用当前生产对应源码生成六人合成牌局，保留第 0 / 20 / 80 / 160 次合法动作的状态。在服务器启动一个低优先级、30 秒超时保护的临时 Node 进程运行计算，实际约 1.62 秒结束；没有启动常驻服务或访问玩家存档。每个状态先预热，再取 5 次样本均值。

| 牌局动作数 | 主持状态 JSON | 规则计算 | 为六人生成当前完整历史快照 | 为六人生成仅近期记录快照 |
| --- | --- | --- | --- | --- |
| 0 | 2.3 KB | 0.05 ms | 0.29 ms | 0.32 ms |
| 20 | 65 KB | 0.91 ms | 8.78 ms | 1.45 ms |
| 80 | 341 KB | 4.20 ms | 38.06 ms | 1.65 ms |
| 160 | 726 KB | 11.04 ms | 76.73 ms | 2.31 ms |

最后一列是评估用对照：投影前只提供最近 3 条历史和最近 10 条事件，并不修改线上实现，也不是建议删掉历史。实际实现应将完整记录持久化并按需分页，实时状态只带增量和未收到的必要事件。

基准进程峰值监控未实施；结束时 RSS 约 101 MiB。该数含多个样本、临时对象和运行时，不能直接乘以桌数，也不能作为完整服务内存上限。规则引擎当前还会复制整段历史，因此搬到服务器之后仍需把实时状态和长期日志分离，避免越打越重。

以上不包含 WebSocket、TLS、数据库提交、并发玩家或真实房间往返时间，不是完整服务器压测。

## 带宽估算

样本中给六位玩家各发一份状态：

| 样本 | 当前六份状态原始 JSON | 当前六份状态 gzip 后 | 仅近期记录六份原始 JSON | 仅近期记录六份 gzip 后 |
| --- | --- | --- | --- | --- |
| 20 次动作 | 281 KB | 13.0 KB | 58.8 KB | 7.2 KB |
| 80 次动作 | 278 KB | 17.2 KB | 64.8 KB | 7.6 KB |
| 160 次动作 | 285 KB | 19.0 KB | 72.3 KB | 10.5 KB |

这是 `gzipSync(level=5)` 的数据大小对照，不代表尚未实现的 WebSocket 已经有相同压缩。Nginx 的 HTTP gzip 不会自动压缩升级后的 WebSocket 数据；实际服务要明确实现消息压缩/增量与背压，再测真实传输量。原有加密 Base64 也不能直接拿来 gzip 期待同样效果。

规划假设：每桌 6 人，全桌每 5 秒发生 1 次规则操作（每分钟 12 次），优化后一次操作向全桌的总下行含必要封装预留 10–25 KB。此值是基于上述压缩样本的设计预算，必须在真实实现中验证。

| 同时牌桌数 | 玩家数 | 仅规则消息预计下行 | 连续活跃一小时出站量 |
| --- | --- | --- | --- |
| 1 | 6 | 0.016–0.040 Mbps | 7.2–18 MB |
| 10 | 60 | 0.16–0.40 Mbps | 72–180 MB |
| 20 | 120 | 0.32–0.80 Mbps | 144–360 MB |
| 50 | 300 | 0.80–2.00 Mbps | 360–900 MB |
| 100 | 600 | 1.60–4.00 Mbps | 720–1800 MB |

不含首次牌图/脚本下载、打开旧历史、观众、重连全量、手势或其他网站业务。如果全桌每秒一次操作，规则消息带宽乘以 5。观众也需要占用下行，不能只按入座数算。

手势不能漏算。当前悬停/选牌最多每 125 ms 发一次，但仅在变化时发送。如果照搬成 6 人都持续 8 Hz、每条约 250 B、分别转给其余 5 人，单桌就约 60 KB/s（0.48 Mbps），20 桌可达 9.6 Mbps。这个是连续变化的规划上界，不是实测常态，也未计协议开销。迁移必须把手势与可靠规则操作分开：合并最新位置、限制房间总频率、丢弃过时手势，不能让它们排在出牌回执前。卡片动画由本地播放，无需逐帧上传。

若暂按 5 Mbps 套餐规划，10–20 桌的规则数据本身很轻，但仍需给手势、冷启动资源和其他服务预留带宽；不能据此承诺 100 桌稳定。100 桌的中后期完整历史计算按本样本及每 5 秒一次操作约消耗 1.76 CPU 秒/秒，未经改造的单 Node 主线程会成为瓶颈。仅近期投影对照约 0.27 CPU 秒/秒，还没包含持久化、压缩等，所以快照优化必须与迁移同步做。

## 建议的实现范围

1. 页面直接使用 WebSocket 连接三龙牌服务。枭熊只提供入口和房间关联，规则动作不再经过它的 LOCAL/REMOTE 消息队列。当前同浏览器后台与页面之间如仍需通信，改用经过来源校验的本地通道，不再转发完整牌局快照到枭熊。
2. 服务器拥有牌堆、规则裁定与持久状态，每个玩家只收公开状态和自己的手牌。保留现有规则引擎、公开/私有投影与牌组身份；不把全桌私有存档发送给普通浏览器。
3. 出牌消息携带唯一动作 ID 和版本；确认持久化后回执，同一动作重试不重复结算。增量断档才重新发完整快照。历史按需分页，实时规则状态不反复克隆全部回放记录。
4. 服务端签发房间/席位凭证，主持邀请与 GM 全能权限有可信授权流程，不能只相信客户端自报 playerId 或 GM。枭熊入口关联和独立网页版分别处理会话恢复。
5. 三龙牌独立进程和资源限制，保留现有角色卡中继，不把它改成同时承担新协议的共享故障点。已打开旧牌局不强制半途迁移，先让新桌选择新通道，验证后切默认。

验收至少包含六个独立客户端的准备/出牌/选择/结算、重复提交、延迟与断线恢复、刷新及主持退出、服务器重启恢复、跨席位私有数据隔离、晚期长历史和真实低带宽；再按 10 → 20 → 50 桌逐级压测并监测 p95/p99 响应、事件循环阻塞、内存、队列和下行速率。正常网络点击到权威确认可设 p95 < 500 ms 为目标，不是本轮已经取得的结果。

如果只想最快缓解，现有枭熊实现也可先减少 REMOTE 历史、去掉提交者重复全量快照并给规则回执优先级。长期方案仍建议自有服务器掌管牌局，这样既绕开广播分包队列，也不再依赖某一位主持浏览器一直在线。
