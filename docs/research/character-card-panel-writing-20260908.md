# 角色卡上传、覆盖和列表写入

## 已确认的问题

对提交 `496bf56` 中真实 `panel-page.ts` 使用 Edge、受控 SDK 和延迟假服务，保存了 11 个基线场景。没有访问线上角色卡 API，子角色卡 iframe 是本地占位。

- 场景 A 发起粘贴 JSON 创建，切到有卡片 B 的场景 B 后才放行服务响应。旧代码此时首次向 B 调用 `setMetadata`，把 A 的新卡加进 B，并广播、打开该卡。这不是假设宿主把较早请求转投新场景。
- XLSX 批量上传有同样的问题，而且第一张完成后还会在 B 自动发起剩余文件的上传。文件选择器本身也没有保留发起场景。
- 删除的元数据已在 A 提交，仅回执挂起；切 B 后回执把 A 的旧列表重新画回 B。下一次正常修改可见性会把这份旧列表写进 B。同场景收到他人新卡后，旧删除回执也会覆盖本地新列表，导致下一次写入丢卡。
- 刷新选择器打开期间角色改变且卡片已被设为 DM 可见，选完文件后仍会首次发起该卡的覆盖请求。
- 可见性写入被 SDK 拒绝后，缓存保留了提前改出的 DM-only 状态；切换语言即可看见与权威元数据不一致的界面，而且没有失败提示。
- 粘贴 JSON 入口和弹窗声称“只读、不保存”，实际调用创建服务。服务返回的卡片 URL 以 `index.html` 结尾；在其后直接追加 `data.json` 也不能通过完整角色卡既有的绝对数据地址检查。

基线还保留了一个双面板同时读写整表的演示：倒序应用依赖夹具的宿主写入假设，不能作为已在 Owlbear 复现的结论。原始记录在本机 `_audit/2026-09-08/cc-panel-write-audit/frozen-baseline.md`。

## 修正行为

一次操作从点击入口、文件选择器或整批拖放开始，记录原场景代次、房间、玩家身份和角色。等待文件、网络响应、XLSX 解析、盾牌修正、元数据读取及写入回执后都核对有效性。切场景、身份改变、关闭页面或目标从可见列表移除会终止后续工作，并取消可取消的请求；新角色仍可按现有规则创建公开卡。没有把玩家操作全部改为 GM 专用。

同一卡片的刷新、删除和可见性操作共用在途状态，文件选择器未返回时也不能重复启动。整批上传只属于发起场景，失败后停止；选择文件期间只禁重复操作，真正上传后才显示上传状态。上传遮罩不挡住关闭按钮。

同一面板中的元数据变更串行执行。每项执行前读取最新完整列表；读取期间收到的较新事件优先。刷新覆盖前重新核对目标；删除回执后再次确认卡片没有被重新加回，才发起服务端删除。刷新服务返回的字段不会覆盖最新的 `visibility` 和 `owner_ids`。

写入回执只有在没有收到较新事件时才应用自己的提案，不再无条件把旧数组赋回缓存。同场景改角色或关窗失败仍等待旧元数据回执，保持本地队列顺序；新场景可以使用自己的队列，不受旧场景挂起请求阻塞。该队列不提供跨客户端原子操作。

初始化时先收到卡片元数据、后收到同场景就绪成功，也会确认写入可用，同时保留已有 iframe。就绪读取失败与元数据到达的两种先后顺序，以及迟到的未就绪答复，都保留同页重试；元数据恢复可读不会抹掉尚未确认连接的重试入口，重试成功不重建已有 iframe。

关闭期间先停止新写入。宿主确认关闭或页面实际卸载后注销读取；如果宿主关闭请求失败，恢复页面、原开窗标记和错误提示，允许再次关闭或继续操作，已取消的上传不会自动恢复。JSON 弹窗可单独取消，Escape 关闭最内层弹窗。粘贴说明和“创建角色卡”按钮明确表示上传、加入当前场景及默认对全员显示。

成功写入后按已捕获的房间和卡片 ID 构造绝对 `data.json` 广播地址，带上房间标识；不再拼接服务返回的 `index.html` URL。原有完整卡片、信息窗及后台监听协议保持兼容。

## 验证方式及限制

```text
node tools/cc-panel-reading-selftest.mjs
node tools/cc-panel-writing-selftest.mjs
node tools/xlsx-shield-selftest.mjs
```

前两个工具使用实际列表页、真实浏览器事件及延迟 SDK/API 边界；写入测试包含服务忽略取消信号仍返回的情况。完整子卡由占位 iframe 提供，不能把它算作真实玩家联合权限验收。第三个工具实际解析两份原件派生的 XLSX，并检查盾牌修正每个等待点的取消边界。最终固定源码、断言数量与独立构建结果记录在 `docs/IMPLEMENTATION_PROGRESS_20260908.md`。

已发往服务器或宿主的写入可能已经完成，取消信号不能撤回它。服务已经创建但尚未加入场景的文件、已提交的覆盖和迟到回执不能伪称自动回滚。本批没有补偿删除陌生文件、改变服务器认证或修改全房间写入协议。列表可见范围仍是发现权限，不是静态文件访问控制。跨客户端同时修改完整元数据数组仍缺少原子比较更新，不能用一个面板内的队列宣称解决。

没有进行线上部署、实际 Owlbear 房间上传或原生 Excel/WPS 重算。真实服务响应、多人网络和宿主关闭的运行验收继续保留。
