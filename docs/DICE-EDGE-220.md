# Edge 骰子加载与限流修复 · 220

日期：2026-10-01（Asia/Shanghai）。用户要求解决 Edge 骰子卡加载、先攻无法投掷并部署。以线上 Suite 219、源码 fb0e915e634db8300bc3c00195a3be257adac8fd 为基线，只发布新版静态前端。

## 确认的根因

线上 vendor/jolt-physics.wasm.js 为 966574 字节，SHA-256 10d2a80544a3d08d06eb0d899d84ff7545e0d10901f494db93f5e045422563eb，与玩家截图逐字符相同。转换 CRLF 为 LF 后为 964712 字节、bcebc61c2a5db94f1b155b2ce1902667f952d9d63baa003b654e9e5d1ff20eb4，与 vendor/lock.json 一致。219 构建只校验 asset-hashes.json，漏掉独立 vendor 锁；开发夹具却替 vendor 归一换行，因而生产包缺陷被遮住。Firefox 成功可以由已有正确缓存解释，但没有读取玩家 Firefox 缓存，不将此推断当作确认事实。

投骰轨迹原来以很短间隔连续广播；周期维护在请求变慢时也可重入、重复排队。SDK 的明确 RateLimitHit 拒绝直接进入 network-receive / 投骰失败。该路径通过故障注入验证，未取得玩家 SDK 完整请求时间线。

## 修复

- 在实际骰子生产构建及打包时合并校验两个锁文件，59 项锁定资产全部验证。只在 CRLF 归一后严格匹配原始散列时恢复字节；其他损坏继续拒绝。Git 属性保留 vendor 脚本和许可的 LF。
- 静态骰子资源使用 dice-assets-220 版本；校验失败在三次预算内使用新重试 URL 与 reload 重取，不要求玩家清角色数据。
- 骰子后台广播与跨 iframe 提交使用有序发送队列，相邻请求至少 100 ms。只重试明确 RateLimitHit 拒绝，退避 800 / 1600 / 3200 ms；超时等未知结果不自动重放。原提交 ID / 权威结果 / 私密权限不变。
- 维护循环不能重入；近期时钟探测不重复发送。轨迹初传未完成时不启动维修/准备超时，接收端按实际分片进度计时。
- 保留 219 单后台引擎、先攻失败不写入、Action 历史和 217 群体骰子的实现；协议仍为 suite-3d-3。
