# 263：小批次投骰启动等待修复

范围为新版 `/suite-dev/`。本轮基线为线上 262（源码 `d9744d9ce4ac84847f5eb1d72b68532b1f16dce1`），隔离工作区来自远端 dev 合并提交 `55c239140c32e680c0f4016fb4099082dbe4134f`。配套 Web 为线上运行的 `e3aafedd089e62a0e533ed1ba76e1d6a693d6989`。原工作区未提交内容保留。

用户确认等待发生在点击后、骰子出现前。复现发现完整轨迹的清单、数据、尾包、确认及开播指令共用 100 ms 发送队列；校时消息等待发送回执时又阻塞了串行接收。小批次的物理计算通常只占其中一部分。

## 实现

- 通过已验证会话的 `tracePacketV1` 能力协商，1～20 枚公开骰子采用自带清单的轨迹包，每片最多 10,000 字节。逐包检查 JSON 总大小不超过 15,000 字节；较大房间清单自动回退。
- 有旧端、未知会话、角色验证尚未完成、暗骰、群体批次或超过 20 枚时，保留原清单和 7,000 字节分片流程。未重新使用此前撤出的 inline 协议字段。
- 所有轨迹仍完整验证 SHA-256、身份、公式、皮肤及结果，然后等待本机和接收端准备。没有抢先显示未经确认的动画。
- 快速包沿用带散列的开播指令、丢片修补、重复消息去重和会话重启保护。单包整包丢失时，定向重试携带原首片；继续播放同一条轨迹。
- 队列在真正空出发送时隙后选择优先级，让投骰可以越过等待中的心跳。保留 100 ms 间距、最多连续八条控制消息、明确限流的有界退避及未知回执不盲目重发。
- 校时和 hello 的发送回执不再占住串行收件通道；校时仍记录实际接收和实际发送时间。

没有改变物理步长、轨迹采样、随机种子、点数、材质、声音、动画时长或已有骰子的碰撞。无损重排压缩仅做过本地研究，收益不足，未进入产品。
